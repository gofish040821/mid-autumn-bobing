# 月满中秋 · 在线博饼

> 六骰听月落，一桌争状元。

一个**真正的实时多人联机**中秋博饼网页小游戏。2~15 位朋友各自用自己的手机或电脑打开网页，进入同一桌，按座位轮流博饼，实时看到同一副骰子、同一个结果。

不是单机 Demo，不是一台电脑上轮流点，也不是前端 `Math.random()` 假装开奖——**骰子由服务器掷，所有人同时看到结果**。

## 一分钟跑起来

需要 **Node.js ≥ 18**。

```bash
npm install     # 安装全部依赖（npm workspaces，一次装好三个包）
npm run dev     # 同时启动服务端(3001) 与 前端(5173)
```

然后打开 <http://localhost:5173>。

进入页面后点「开一张新桌」，会拿到一个 **5 位房间码**（如 `7K3FZ`）。想验证联机效果，点「复制邀请链接」发给**无痕窗口**或另一台设备，对方打开就自动坐进同一桌——不用手抄房间码。

> 人满 2 位，房主点「开始博饼」，或者凑满 15 人自动开局。
>
> 同一台服务器上可以同时开很多桌，互不干扰：朋友各自开各自的桌，链接发错了、房间码打错一个字母，都会明明白白告诉你「找不到这一桌」，而不是把你丢进一间空屋子干等。

### 其他命令

| 命令 | 作用 |
| --- | --- |
| `npm run dev` | 同时启动服务端与前端（开发用，支持热更新） |
| `npm run dev:server` | 只启动服务端（`tsx watch`，改代码自动重启） |
| `npm run dev:client` | 只启动前端（Vite） |
| `npm run typecheck` | 三个包全量类型检查 |
| `npm test` | 运行规则、引擎、房间和客户端揭晓时序测试（不需要启动服务） |
| `npm run test:e2e` | 端到端联机验收：起 4 个真实 Socket.IO 客户端连真实服务端，跑完整局（需先启动服务端） |
| `npm run test:multiroom` | 多房间隔离验收：开几张桌同时玩，逐条断言各桌的骰子、广播、玩家互不串线（需先启动服务端） |
| `npm run test:browser` | 浏览器验收：用系统 Chrome 真点一遍，截图存 `screenshots/`（需先 `npm run build && npm start`） |
| `npm run build` | 构建前端到 `client/dist` |
| `npm start` | 生产模式启动服务端（会自动托管 `client/dist`） |

生产部署最短路径：

```bash
npm run build && npm start
# 打开 http://<你的IP>:3001 —— 服务端会把前端和 Socket.IO 一起托管
```

## 玩法

1. **开桌 / 入席**——打开网页，点「开一张新桌」拿到房间码，或者用朋友给的房间码 / 邀请链接进他那一桌；取个雅号（或点「随机取名」），进入大厅。无需注册。
2. **开席**——满 2 人后房主点「开始博饼」；满 15 人则 5 秒后自动开席。
3. **轮流博饼**——按座位顺序，轮到你时点那颗朱砂大按钮。每回合 5 秒，超时由服务器自动代掷（不会卡住整桌人）；已经掉线的人只等 3 秒。
4. **看结果**——六颗骰子落定，按判奖表从高到低匹配奖项，发奖、加分、写进日志。
5. **追状元**——第一位博出状元骰型的人成为「状元候选」，其余每人按座位顺序再各追一次。**反超比两级：先比状元等级，等级相同再比剩余点数之和；两级都持平才先出现者优先；而状元本人再博状元时，以他最后一次的成绩为准。** 追完一圈回到普通回合接着博——状元不是终局信号，之后有人刷新榜首还会再开一轮。
6. **博到饼尽**——一秀、二举、三红、四进、对堂五样饼全部博完，本局收席，出积分榜。状元拿走唯一的状元奖（他的状元骰型基础分 + 100 分）。**约十分之一的牌局到最后都没有状元**，那一份饼原封留在桌上。

刷新页面、断网、切后台再回来，座位、昵称、积分、奖品、当前回合都会自动恢复。

## 页面与开奖演出

- 暖白底色、淡月与一盏灯笼，减少装饰和阴影；桌面三栏，手机单栏，手机默认收起题名榜和博饼记录。
- 骰子使用 CSS 3D 六面立方体、透视旋转与弹跳动画，不额外加载 WebGL 或物理引擎。
- 所有奖项统一翻滚 1800ms。动画中缓存服务端快照，落定后才同时更新点数、积分、库存、记录、状元提示与开奖音效；减少动态效果模式也保持同样的揭晓等待。
- GitHub 贡献者及个人主页链接显示在页脚，游戏界面不显示访问统计。

## 用手机一起玩（局域网）

服务端和前端都监听了 `0.0.0.0`，同一 Wi-Fi 下的手机可以直接访问。

1. 在电脑上执行 `npm run dev`。
2. **启动时终端会打印局域网地址**，形如：

   ```
   ➜  本机:    http://localhost:5173
   ➜  局域网:  http://192.168.1.23:5173
   ```

   如果没有打印，也可以自己查：Windows 用 `ipconfig`，macOS/Linux 用 `ifconfig` 或 `ip addr`，找 `192.168.x.x` / `10.x.x.x` 这类地址。

3. 手机连**同一个 Wi-Fi**，浏览器打开 `http://192.168.1.23:5173`。
4. 每台设备取一个不同的雅号，就能坐在同一桌。

> **连不上？** 多半是电脑防火墙拦了 5173 / 3001 端口。
> - Windows：控制面板 → Windows Defender 防火墙 → 允许应用通过防火墙，勾选 Node.js；或临时关闭专用网络防火墙测试。
> - macOS：系统设置 → 网络 → 防火墙 → 选项，允许 Node 接受传入连接。
> - 另外确认路由器没有开启「AP 隔离 / 客户端隔离」，否则同一 Wi-Fi 下设备之间无法互访。

## 部署到公网（让别人在任何网络下都能进）

### 先说清楚：GitHub Pages / Vercel 这类托管**跑不了**这个游戏

这不是配置问题，是架构问题。这个游戏的三根支柱全在服务端：

- **骰子是服务端掷的**——客户端只能提交「我要掷」，不能提交点数；
- **房间、回合、30 秒超时**全在服务端内存里；
- 客户端与服务端靠 **Socket.IO 长连接**通信。

| 托管方式 | 能不能跑 |
| --- | --- |
| GitHub Pages / Netlify 静态托管 | ❌ 只发文件，不执行 Node，不维持长连接 |
| Vercel Functions | ❌ 2026 年 6 月虽然支持了 WebSocket，但**单条连接上限 5 分钟**，一局博饼远超这个时间 |
| **Render / Railway / Fly.io / 自己的服务器** | ✅ 能跑常驻 Node 进程与长连接 |

把前端单独丢到静态托管上，页面能打开、能画，但一点「开始博饼」就永远卡在连接中——**看起来像坏了，其实是根本没有服务端**。

### 部署只要一个服务

`server/src/index.ts` 里 Express 既托管 `client/dist` 静态页、又挂 Socket.IO，**前后端本来就在同一个进程、同一个源上**。因此：

- 不需要「前端一个域名 + 后端一个域名」；
- 不存在跨域问题，不用配 CORS；
- 平台给你一个地址就够用。

### Render（仓库里已带好 `render.yaml`）

1. 把仓库推到 GitHub。
2. 打开 [render.com](https://render.com)，用 GitHub 账号登录。
3. **New +** → **Blueprint** → 选中本仓库。Render 会读 `render.yaml`，自动填好构建与启动命令。
4. 等首次构建完成（约 2~5 分钟），拿到形如 `https://mid-autumn-bobing-xxxx.onrender.com` 的地址。

这个地址可以发给**任何网络下的人**（微信直接发就行），不需要同一个 Wi-Fi。

想手动填的话就两条：

| 项 | 值 |
| --- | --- |
| Build Command | `npm install --include=dev && npm run build` |
| Start Command | `npm start` |

### 免费档的真实限制（是取舍，不是 bug）

1. **15 分钟没有入站流量就休眠**，下次访问冷启动约 1 分钟。玩的时候每 30 秒有人掷骰，有流量就不会休眠。
2. **所有房间的状态都是纯内存的**（`RoomManager` 持有一张 `Map<房间码, GameEngine>`）。进程一休眠或重新部署，**所有桌**的牌局一起没——免费档是单进程，做不到「只掉一桌」。对十几分钟一局的牌来说这个代价可以接受。
3. 玩家**短暂掉线**是安全的：`guestId + sessionToken` 会重连回原座位，`ABANDON_GRACE_MS` 兜住「全员掉线导致房间死锁」。但**服务进程重启**救不回来。

想彻底避免休眠，就升到付费档，或者干脆用自己电脑 + 局域网 / 内网穿透。

### 部署前必查的一件事

`client/src/socket/socketClient.ts` 里的连接地址**必须由同源推导**。这里曾经写死过「非 localhost 就直连 `:3001`」，在云平台上必然连不上——平台只给一个 https 域名，没有 3001 这个端口。**这个 bug 在本地怎么测都测不出来**，因为本地永远命中 localhost 那一支。

要复现云端的失败条件，可以在本地用「非 localhost 域名 + 非 3001 端口」模拟：

```bash
PORT=10000 npm start
# 另开一个终端（127.0.0.2 属于 127.0.0.0/8 回环段，但不是 localhost）
BROWSER_TEST_URL=http://127.0.0.2:10000 npm run test:browser
```

## 在一台电脑上开 4 个客户端测试

一个人也能验证联机逻辑：

**方法一：多个窗口（最简单）**

1. 普通窗口打开 <http://localhost:5173>，点「开一张新桌」，拿到房间码；
2. 点「复制邀请链接」——链接形如 `http://localhost:5173/?room=7K3FZ`；
3. 把这个链接分别粘进 3 个无痕窗口。

**关键是第 2 步**：直接在新窗口里敲 `localhost:5173` 是**没有房间码**的，四个窗口会各自开各自的桌，然后你会以为联机坏了。房间码就带在那个 `?room=` 上，链接复制过去才坐得进同一桌。

> 必须用无痕窗口：身份靠 `localStorage` 里的 `guestId` 区分，同一个浏览器配置文件会被认成同一个人（服务端会拒绝重复入席并提示「这个浏览器已经有座位了」）。

**方法二：不同浏览器**

Chrome / Edge / Firefox / Safari 各开一个，都把那条 `?room=` 邀请链接粘进去。

**方法三：手机 + 电脑混合**

电脑开 2 个无痕窗口，2 台手机各开一个（手机扫不出码就手输那 5 位房间码）——最接近真实聚会场景。

**验证清单：**

- [ ] 4 个窗口都能进大厅，看到彼此
- [ ] 房主点「开始博饼」后，4 个窗口**同时**跳到游戏页
- [ ] 轮到某人时，只有**他的**「博饼」按钮是亮的
- [ ] 他点下去，**所有**窗口同时播放同一段骰子动画，落定后是同一组点数
- [ ] 有人博出四颗四点 → 所有窗口同时进入追状元
- [ ] 关掉一个窗口再打开 → 自动回到原座位，积分奖品都还在
- [ ] 某个窗口什么都不做 → 30 秒后所有人看到「系统替他掷出了骰子」

## 架构：为什么它是「真·联机」

### 服务端权威（这是整个项目的地基）

**客户端只能做一件事：说「我要博饼」。**

```ts
// shared/src/events.ts —— 客户端能发的全部内容
game:roll(turnId: string, actionId: string)   // 没有 dice、没有 award、没有 score
```

- 骰子由 `server/src/game/DiceService.ts` 生成：六颗均匀的 1~6，**没有加持、没有保底、没有任何为了凑出某个奖项而构造的点数**。它甚至不接受外部的随机源，只接受可注入的 `Rng`（测试里注入确定性序列）。
- 奖项由 `RuleEngine` 判定，积分、库存、状元全部在服务端计算。
- 客户端提交的 `dice` / `award` / `score` / `inventory` / `champion` 一律**不存在于协议里**，想伪造也无从下手。

### 事件 + 全量快照广播

每次状态变化，服务端同时下发：

1. **语义事件**（`roll:started`、`roll:result`、`champion:updated`…）——告诉客户端「放什么动画、放什么音效」；
2. **完整快照** `GameSnapshot`——携带 `stateVersion`。

客户端用 `stateVersion` 做单调校验，**永远不用旧状态覆盖新状态**。因此丢包、乱序、切后台回来都能自愈：快照一到，界面自动对齐。

### 服务端时间权威

倒计时以服务端下发的 `deadlineAt` 为准，客户端用 `serverTimeOffset`（= `snapshot.serverTime - Date.now()`）校正本地时钟。**手机时间不准也不会显示错乱**，而且客户端倒计时纯粹是展示——真正的超时判定在服务端。

### 防重复开奖

每个回合有唯一 `turnId`，每次点击带唯一 `actionId`。服务端用 `(turnId, actionId)` 做幂等键，并且回合状态机严格限制 `WAITING → ROLLING → RESOLVING`。

所以：**双击按钮只会博一次**，弱网重发也只会博一次。

### 掉线与重连

- 身份 = `guestId`（浏览器生成）+ `sessionToken`（服务端下发）。
- 刷新 / 断线重连时带上 token，服务端把连接重新绑回原座位——**昵称、座位、积分、奖品、游戏阶段全部恢复**。
- 游戏进行中，掉线玩家**永远不被移出座位**，只标记 `offline`；轮到他时照样自动代掷，整桌不会卡住。
- **代掷的等待时间分两档**：在线的人是 30 秒（给他思考的时间），**已经离线的人只有 10 秒**。人都不在了，等满 30 秒只是让一桌人陪着一个空座位干等；掉线那一刻如果正好轮到他，截止时间也会立刻从 30 秒缩短到 10 秒（`deadlineAt` 一起改，客户端的倒计时才不会和服务端对不上）。
- 只有在**等待大厅**里，掉线超过 60 秒才腾出座位给别人。
- **房主走了，这一桌就作废**（详见下一节）。
- **散场回收**：牌局进行中如果**一个人都不在线**了（大家都关了页面、断网、手机没电），房间不会永远卡死。等 2 分钟仍然没人回来，这一局就作废、房间退回大厅，下一组人推门进来就能直接开新局。

### 多房间：一桌一个引擎

服务器同一进程里可以并行开很多桌。结构很薄：

```
RoomManager            Map<房间码, GameEngine>     ← 只管「哪张桌在哪」
  └─ GameEngine        玩家 / 骰子 / 库存 / 计时器   ← 完全自包含，不知道别的桌存在
PlayerManager          socket.id → (房间码, playerId)  ← 路由依据
```

桌与桌之间**没有任何共享状态**，所以「A 桌在追状元」和「B 桌刚开席」天然互不影响。要不要加锁、要不要隔离状态，这类问题在结构上就不存在。

几个刻意的选择：

- **房间按需创建，不预建房间池。** 第一次有人点「开一张新桌」才建，空置满 2 分钟回收（记录时间戳 + 定期扫描，而不是每桌挂一个定时器——后者会在反复创建回收中攒下一堆定时器句柄）。
- **房间码由服务端生成，客户端不能指定。** 字母表剔掉了 `0/O/1/I/L`，31 个字符取 5 位 ≈ 2860 万种组合；建房时仍对着现存房间查重。
- **进不存在的房间不会顺手建一张。** 打错一个字母就凭空多出一间空房，而人会坐在里面等一个永远不会来的朋友。所以 `room:join` 只查不改，建房必须走 `room:create`。这条有测试盯着。
- **路由依据是 socket 自己记住的房间**（入席成功时写进 `socket.data`），不是 payload。客户端只能在过闸那一刻选一次房间，之后所有动作都发生在同一张桌，没法中途「跳到」别人的房间里去。换桌时会先退出旧的 Socket.IO 房间，否则旧桌的广播还会继续漏过来。
- **`playerId` 只在房间内唯一。** 每张桌都从 `player_0001` 开始数，所以 A 桌和 B 桌一定各有一个 `player_0001`，而他们**不是同一个人**。socket → 玩家的绑定必须带上房间码，否则 B 桌的人会拿到 A 桌的 playerId，接着用别人的身份掷骰子——两边看起来都「正常」，只有积分记错了人。这是整个改造里最隐蔽的一处，`rooms.test.ts` 和 `npm run test:multiroom` 都在盯它。
- **每次入席，当事人会额外收到一份快照。** `engine.join()` 广播 `room:playerJoined` 的那一刻，这个 socket 还没进房间，收不到自己的入场广播；不补一份，新人就得干等下一次广播才同步。顺序上仍然先 `engine.join` 再 `socket.join`——这样入席失败时（满员、身份冲突）完全不碰 socket 的房间归属，换桌失败不至于把人从原来的桌上踢下来。
- **换桌会回头告诉旧桌「这个人走了」。** 少了这句，旧桌会永久留着一个「在线」的幽灵座位：人明明在别桌玩，这边还占着位子、人数也算他一份，而且因为 socket 已经退出旧房间，它的 `disconnect` 永远不会来，谁也清不掉。大厅里直接退座，牌局进行中则只标记离线——中途抽走座位会把那一局搅乱。

### 房主离席 = 整桌作废

**开桌的人一走，这一桌立刻解散**，剩下的人收到一句「房主已离席，这一桌散了」并被请回入席页。房间从列表里消失，所有人的座位凭证一并作废。

刻意**不做房主移交**：这张桌是房主开的、房间码是他发出去的、牌局也是他起的头。换个人接手，剩下的人是在玩一局「主人已经走了」的牌，谁都不知道还该不该继续——不如干脆散伙，让剩下的人重新开一张桌来得清楚。

#### 代价是明摆着的

**房主只要断线，全桌陪葬。** 具体包括：

- 刷新页面
- 切到别的标签页 / 切到别的 App
- **手机息屏**

服务端认定「人走了」只需要一次传输层断开，以上三种都会触发。所以：

> ⚠️ **手机上开桌 → 复制邀请链接 → 切到微信粘贴发送 → 手机息屏，这一桌就没了。**
> 朋友们点开链接会看到「找不到这一桌」。

这条与空房回收里那句「连续两次扫描才回收，中间那段时间留给『创建 → 朋友点进来』」的心意是**冲突**的：回收逻辑特意留了宽限期，而房主离席是零宽限。这不是疏漏，是按「一断线立刻作废」的要求做的选择，但用手机发链接时确实会撞上。

真要绕开，有两个不改代码的办法：**先把人都拉进来再开桌**，或者**桌面端开桌发链接**（电脑不会息屏）。如果希望房主短暂掉线还能回来续上，那就得给「房主离席」加一个宽限期——目前是**没有**的。

#### 实现上容易踩的两个坑

- **判断必须在引擎动手之前。** `engine.disconnect()` 一调用，`ensureHost()` 会立刻把房主移交给别人；再想问「刚走的这位是不是房主」，答案永远是「不是」。所以是 socket 层先看 `engine.hostId`，确认是房主就直接把整桌关掉。
- **顺序不能反。** 先 `io.to(roomId).emit('room:closed')`，再 `players.unbindRoom()`，最后才 `rooms.destroy()`。等 socket 都退出了房间，这条通知就没人收得到了。

客户端这边还有一处**不能想当然**的地方：收到 `room:closed` 时**不要把 `snapshot` 清成 `null`**。退场是靠 `hasJoined` 触发的，而 `AnimatePresence` 的 `mode="wait"` 会把旧页面继续挂着、等它淡出完（340ms）才挂新页面——这段窗口里如果快照是空的，游戏页整棵子树当场渲染成空，退场动画的「已完成」回调再也不会触发，新页面永远等不到上场机会，**用户看到的是白屏**。这个 bug 就是 `npm run test:browser` 抓出来的，`resync` 遇到 `INVALID_SESSION` 时也是同样的处理（只置 `hasJoined`，不动快照）。

### 前后端节奏一致

骰子动画播多久、演出放多长、延迟多久进下一回合——这三件事共用 `shared/src/timing.ts` 里的一张表：

```ts
export const ROLL_TIMING: Record<AwardId, { diceMs: number; celebrationMs: number }> = { … }
```

服务端读它来决定「什么时候推进下一回合」，客户端读它来决定「动画播多久」。**两边不可能跑偏**；想整体调快调慢，只改这一个文件。

**七个状元等级共用一个「状元」奖品**，全桌只有一个，只发给最终状元。强弱比较分两级：

1. 先比 `championRank`（插金花 7 → 四点红 1）；
2. 等级相同再比**剩余点数之和** —— 同为四点红时 444456（余 11）大于 444426（余 8），五红 / 五子登科比剩下的那一颗。

两级都持平才轮到「先出现者优先」。固定组合（插金花、六杯红、遍地锦、六抔黑）没有余数，同档之间一律先到先得。比较函数是 `shared/src/rules.ts` 的 `championTiebreak`。

**唯一的例外是现任状元本人**：他再博出状元档时直接把自己的成绩换成最后一次——哪怕比之前小，甚至档次更低（先五子登科、后四点红就降到四点红）。这属于「刷新自己的成绩」，不算易主，也不会弹「金榜易主」，但成绩变了就会重新开一轮追状元，让对手按新的成绩再追。

### 奖品库存：一桌饼是定量的

| 奖品 | 份数 | 自然概率 | 期望掷多少次博完 |
| --- | ---: | ---: | ---: |
| 一秀 | 32 | 37.2942% | 86 |
| 二举 | 16 | 19.9331% | 80 |
| 三红 | 4 | 5.3584% | 75 |
| 四进 | 8 | 4.0188% | 199 |
| 对堂 | 2 | 1.5432% | 130 |
| 状元 | 1 | 1.2024% | — |
| **合计** | **63** | | 「期望掷多少次博完」= 份数 ÷ 该池自然概率 |

**份数是传统会饼的经典配比，人工定死，写在一张表里**：

```
一秀 32 · 二举 16 · 三红 4 · 四进 8 · 对堂 2 · 状元 1     共 63 份
配比 32 : 16 : 8 : 4 : 2 : 1，也就是传统会饼的 1 : 2 : 4 : 8 : 16 : 32
```

代码在 `server/src/config/prizes.ts` 的 `PIECES` 表，**要调配货就改那一张表，它是唯一的旋钮**。

⚠️ 注意这**不是**按概率配的，而且刻意如此：三红自然比四进常见（5.36% vs 4.02%），份数却只有四进的一半。早先的版本确实按「份数 ∝ 自然概率」算，那样五个池子的期望清空时间都落在 65~85 掷、「谁都不是短板」；换成传统份数就把那个性质换掉了，代价是**四进一个人拖后腿**——它要 199 掷才清空，实测 **72% 的牌局最后都在等它**，对堂以 23% 排第二。这让一局大约长了一倍（见下一节的实测），换来的是这组数字就是传统会饼本来的样子，玩家一眼认得。

**份数与人数无关。** 一张会饼是定量的，2 人和 15 人博的是同一张饼——所以一局有多长，跟桌上坐了几个人没关系。

**库存领完不补**：骰型照常显示，但标注「奖品已领完」，不发奖也不加分。

## 博到饼尽：本局什么时候结束

### 规则

**一秀、二举、三红、四进、对堂这五样饼全部博完，本局收席。**

就这一条。没有固定轮数，没有时间上限。

**状元不参与收席判定。** 博出状元照常开一轮追状元，追完回到普通回合接着博，一直到五样普通饼都博空为止。这不是疏漏——`consumePrize` 对状元档一律返回 `deferred`（掷出那一刻不扣库存，只在结算时发给最终状元），所以它本来就不可能被博空，算进收席条件就成了一道永远打不开的门。

### 骰子是纯随机的

六颗骰子**永远**是均匀的 1~6，服务端是唯一来源，任何阶段都不做干预，**不论一秀还是状元，全看运气**。

第一版里为了让每局都能收尾，曾经有过两层「人为改点数」的机制——**月华加持**（第二轮起每次没出状元就累积一点额外概率，命中就直接构造一副状元骰子）和**状元保底**（第 5N 次掷骰直接构造状元骰子）。两者都已**整个删除**。现在的 `server/src/game/DiceService.ts` 只剩下 `randomFace` / `rollRawDice` 两个函数，普通回合和追状元回合走的是同一个入口、同一套均匀随机。

删掉之后，**约十分之一的牌局一个状元都博不出来**。这是正常结局，不是异常：此时 `result.champion === null`，状元那一份饼原封留在桌上，结算页显示「饼尽月落」。

（这个比例同时取决于状元档概率和一局掷多少次：牌局越长，撞上状元的机会越多。现在 63 份一桌中位约 209 掷，所以是约十分之一；早先 57 份约 111 掷时，这个数是四分之一。）

### 一局有多长

20000 局模拟（含追状元阶段的额外掷骰）：

| 人数 | 均值 | 中位 | p75 | p90 | p99 | 无状元 | 追状元次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 219.4 | 209 | 260 | 316 | 445 | 9.7% | 1.24 |
| 4 | 220.1 | 209 | 261 | 316 | 447 | 9.7% | 1.23 |
| 8 | 220.3 | 210 | 260 | 317 | 445 | 9.5% | 1.22 |
| 15 | 220.6 | 209 | 260 | 316 | 448 | 9.7% | 1.20 |

**人数不影响局长度**，四档几乎一模一样——这是「一张会饼定量」的直接结果。追状元阶段的掷骰同样会扣库存（`GameEngine` 里 `consumePrize` 在 `isChase` 判断之前无条件调用），所以人多带来的额外追击掷数并不是白掷，它们一样在推进饼尽。

各池期望清空掷数（20000 局，与上表的「份数 ÷ 概率」吻合）：

| 池 | 份数 | 均值 | p99 | 「最后才清空」占比 |
| --- | ---: | ---: | ---: | ---: |
| 一秀 | 32 | 85.8 | 117 | 1.0% |
| 二举 | 16 | 80.3 | 129 | 1.0% |
| 三红 | 4 | 74.4 | 184 | 2.6% |
| **四进** | **8** | **199** | **395** | **72.5%** |
| 对堂 | 2 | 128 | 425 | 22.7% |

按每次掷骰加权均值约 2.6 秒（`shared/src/timing.ts`）折算：

- **中位约 9 分钟**，p90 约 14 分钟，p99 约 19 分钟；
- 以上**只是动画时间**，不含玩家思考时间，所以实际会更长；
- **没有上限**。80000 局里最长的一局是 840 掷（约 36 分钟）。长尾是这套规则的固有性质：**四进只有 4% 的概率、却要博满 8 份**，72% 的牌局都在等它；对堂（1.5%、2 份）排第二。这不是 bug。
- 一个反直觉的推论：**对堂每局必定恰好出现两次**（它是收席条件，所以那两份一定都被博走）。而三红虽然比四进常见，却只有 4 份、通常远在收席之前就博空了——**「中得越多、配得越多」在这里不成立**，别再照着那句话去理解份数。

**顺带一个副作用：掷骰历史是滚动窗口。** 快照里的 `rollHistory` 只保留最近 `MAX_ROLL_HISTORY`（300）掷、`gameLog` 只保留最近 200 条（见 `server/src/config/gameConfig.ts`）。这两个上限是为了压住广播体积 —— 快照挂在每一次开奖广播上发给全桌。旧配货一局 111~177 掷，从来碰不到；现在一局中位 209 掷，**一半以上的局都会溢出**，最早的掷骰会从头部丢掉。

这不影响玩家看到的东西：「今夜博饼纪事」按最新在前渲染，丢掉的正好是滚出视野的那些；而 `rollHistory` 客户端根本没有读（只有冒烟脚本拿它对账）。但**别为了「留下完整对局记录」去调大这两个数** —— 那是在给每一次广播加负担。

`scripts/e2e-smoke.mjs` 会真的打完一局（**通常 10~20 分钟**，长尾能到 40 分钟，别提前掐掉），并给出实测掷骰次数与用时。它也是唯一一个真打完整局的冒烟脚本——正因为这么慢，日常改动跑 `test:multiroom` / `test:browser` 就够了，这个留作压轴。

### 追状元

首位状元出现后：

1. 他从**下家开始**按座位顺序，其余每人各追加**一次**。
2. 反超比两级：先比**状元等级**，等级相同再比**剩余点数之和**（如 444456 大于 444426）；两级都持平才「先出现者优先」。**挑战者若就是现任状元本人，则无条件换成他最后一次的成绩**（可能更小，甚至降到更低档）。
3. 只追**一圈**（N−1 次），不延长。
4. **追完不是收席**——回到普通回合接着博。之后若有人再博出更高的状元档，榜会再次易主，并**再开一轮**追状元。（正在追状元的过程中博出状元档只夺榜，不会嵌套开新一轮。）
5. 五样饼博空收席时，最终状元拿走唯一的状元奖：**他的状元骰型基础分 + 100 分**。

这里有个容易踩的坑：**状元档在「掷出那一刻」不发奖也不加分**（那份状元的归属还没定），要等收席时才统一发给最终状元。被反超的人一分也拿不到。这条也有测试守着。

### 改判奖规则 / 积分

- 改判定条件：改 **`server/src/game/RuleEngine.ts`** 里的 `PREDICATES`。

### 改奖品数量 / 改牌局长度

**份数是一张手填的表** —— 编辑 **`server/src/config/prizes.ts`** 里的 `PIECES`：

```ts
const PIECES: Record<PrizeKey, number> = {
  ONE_SHOW: 32, TWO_LIFT: 16, THREE_RED: 4,
  FOUR_ADVANCE: 8, DUITANG: 2, CHAMPION: 1,
};
```

**这就是唯一能调局长度的地方**，改它就够了。两条硬约束：

1. **每一样都必须 ≥ 1。** 五样普通饼全都是收席条件（见同一文件里的 `ENDING_PRIZE_KEYS`），配成 0 会让「博到饼尽」在开局那一刻就成立，牌局直接收席。`inventory.test.ts` 有断言守着这一点。
2. **要改就改对地方。** `inventory.test.ts` 会把配比钉死在 1:2:4:8:16:32、总数 63，改完必须同步更新那条断言和 README 的库存表。

想反推长度的话，每个池子的期望清空掷数大致是 `份数 ÷ 该奖池的自然概率`（自然概率见 [奖品库存](#奖品库存一桌饼是定量的) 那张表）。当前配置下最短的池子（三红 75 掷）和最长的一个（四进 199 掷）差了快三倍，而**局长度由最长的那个决定** —— 所以调配货时先看四进。

> 无论怎么改，**单局长度没有上限**（见 [博到饼尽](#博到饼尽本局什么时候结束)），当前配置下中位约 9 分钟、p99 约 19 分钟纯动画时间。

改完记得同步更新 `shared/src/awards.ts` 里各奖项的 `rule` 文案（规则弹窗会显示）。

### 端到端联机验收

单元测试是直接调用 `GameEngine` 的，它证明不了「真的能联机」。所以另有一个验收脚本，起 **4 个真实的 Socket.IO 客户端**连到**真实运行的服务端进程**，跑完整的一局：

```bash
# 终端 A
npm run dev:server
# 终端 B
npm run test:e2e
```

**每次上千项检查全部通过**（牌局长度完全由骰子决定，逐回合那一节按每掷约 6 条算，掷数越多条数越多；上面那局 419 掷对应 2584 条）。

⚠️ 它跑的是**完整一局**，现在是「博到饼尽」，63 份一桌中位约 209 掷，所以**通常要 10~20 分钟**，长尾能到 40 分钟——别提前掐掉。脚本里有三条各自独立的收工线（掷骰 1500 次、空转 4000 次、墙钟 60 分钟），都压在两万局实测的最坏值之上留足余量，正常的局碰不到。

也正因为它这么慢，**日常改动不必跑它**：`npm run test:multiroom` 与 `npm run test:browser` 都是秒级的，覆盖了绝大多数回归面。这个脚本留作发版前的压轴。

它验证的是单元测试覆盖不到的东西：

- 四个人是否**真的互相看得见**、座位是否按入席顺序排定
- 每一次开奖，**四个人收到的骰子是否完全相同**（逐次比对 `dice.join()` 与 `awardId`）
- `stateVersion` 是否**单调递增**，有没有客户端收到过倒退的状态
- 非当前回合玩家**代博被拒**、同一回合**换 actionId 也博不了第二次**
- 结算：**按有没有状元分成两支**——有则恰好一人被标记、只有他持有状元奖品、他的积分 = 逐掷得分 + 基础分 + 100；无则无人被标记、无人持有状元奖品、**状元库存仍是 1**
- 收席那一刻**五样普通饼确实全部为 0**，且开局配货 `initial` 全程未被改动
- 断线重连：座位 / 积分 / playerId 全部不变，**伪造 token 的 sync 被拒**
- 再来一局：库存重建、计数器归零、**第二局 turnId 不与第一局撞车**

脚本每次**现开一张新桌**，所以不挑服务端状态：不用重启、也不会和别人的牌局互相干扰（如果刚才跑过浏览器验收，直接跑就行）。

```bash

```

## 常见问题

**Q：为什么同一个浏览器开两个标签页，第二个人进不来？**
身份靠 `localStorage` 里的 `guestId` 区分。同一个浏览器配置文件会被认成同一个人，服务端会提示「这个浏览器已经有座位了」。请用**无痕窗口**或另一个浏览器。

**Q：手机连不上？**
99% 是防火墙。见 [用手机一起玩（局域网）](#用手机一起玩局域网) 的排查步骤。也确认路由器没开 AP 隔离。

**Q：刷新页面会掉座位吗？**
不会。座位凭证存在 `localStorage`，刷新后自动重连回原座位，昵称、积分、奖品、游戏阶段全部恢复。

**Q：某个玩家掉线了怎么办？**
整桌不会被卡住。轮到他时只等 10 秒（在线的人是 30 秒），服务器自动替他掷。他回来只要刷新页面就能接着玩。

**Q：房主退出了会怎样？**
这一桌立刻作废，所有人被请回入席页。注意「退出」包括刷新、切后台和**手机息屏**——服务端只认连接断没断。所以**别用手机开完桌再切去微信发链接**，那一桌会当场散掉；先把朋友拉进来，或者在电脑上开桌。详见 [架构 · 房主离席 = 整桌作废](#房主离席--整桌作废)。

**Q：大家都关了页面，这局会一直卡在那儿吗？**
不会。全员离线满 2 分钟就会判定散场：本局作废，房间退回大厅（详见 [架构 · 掉线与重连](#架构为什么它是真联机)）。这个宽限是刻意的——切后台、Wi-Fi 抖动、手机息屏都会在一两秒内重连回来，那种短暂掉线不该毁掉整局牌。要调这个时间就改 `ABANDON_GRACE_MS`，或起服务时用环境变量覆盖：

```bash
ABANDON_GRACE_MS=60000 npm start
```

**Q：一局大概多久？**
中位约 9 分钟，p90 约 14 分钟（纯动画时间，不含思考时间）——**没有上限**，因为要硬等四进那 8 份。骰子完全随机，所以一局到底是 200 掷还是 400 掷，事前谁也说不准。完整分布见 [博到饼尽](#博到饼尽本局什么时候结束)。

**Q：为什么界面不显示具体的状元概率？**
这是刻意的，而且**全站统一**：规则弹窗只描述机制（「六颗骰子每掷一次都是均匀的 1~6」），不写百分比。原因有两层：一是玩家盯着「还差几把」做最优决策，就不像博饼了；二是具体数字是随时可调的参数，写死在文案里，改了参数就会说谎。

想知道确切数值，看 `shared/src/awards.ts`（判奖表，唯一的真相）和 `server/tests/rules.test.ts`（穷举 6⁶ 数出来的各奖项组合数）——要验证文案没跑偏，`scripts/browser-smoke.mjs` 会扫规则页，拒绝「必出 / 必中 / 保证 / 一定 / 必定 / 包出」这些词，也拒绝写死百分比。

**Q：能同时开多个房间吗？**
能。每一桌就是一个自包含的 `GameEngine` 实例，由 `RoomManager`（`server/src/room/`）按房间码保管，桌与桌之间不共享任何状态——各自有自己的玩家、骰子、库存和计时器。默认最多 200 张（`MAX_ROOMS`）。详细设计见 [架构 · 多房间](#架构为什么它是真联机)。

**Q：房间码会撞车吗？**
字母表刻意去掉了 `0/O/1/I/L` 这些念出来、抄下来都容易错的字符，剩下 31 个，取 5 位——约 2860 万种组合。建房时仍会对着现存房间查重，撞了就重摇，最多试 8 次。房间码由**服务端**生成，客户端不能指定。

**Q：房间开着没人用，会一直占着吗？**
不会。大厅里一个人都没有的桌，闲置满 2 分钟（`EMPTY_ROOM_TTL_MS`）就被回收，连带里面的计时器一起销毁。牌局进行中的桌不会被回收——它有自己的散场判定（见上一条），作废回大厅、人走空之后才轮到回收。

**Q：数据存在哪？**
全部在内存里，没有任何数据库依赖。服务端重启后所有房间清空，客户端会提示重新入席。这是刻意的：一局游戏就几分钟，落库的复杂度不值得。

> 代价要说清楚：免费实例是**单进程**的，所以重启（或在 Render 免费套餐上闲置 15 分钟休眠）会同时清掉所有房间，而不是只影响一桌。对十几分钟一局的牌局来说这个代价可以接受。

**Q：贡献者列表如何更新？**
修改 `client/src/components/Common/SiteFooter.tsx` 顶部的 `CONTRIBUTORS` 常量。

**Q：后台统计会跨重启保留吗？**
不会。统计只在内存里，服务进程重启后归零，见 [项目贡献者与后台统计](#项目贡献者与后台统计)。

## 设计取舍

- **为什么用事件 + 全量快照，而不是增量补丁？** 一局最多几百次掷骰，快照体积很小；换来的是「任何客户端在任何时刻拿到快照都能立刻对齐」的强自愈能力。增量补丁省的那点带宽，不值这个复杂度。
- **为什么把「人为改点数」的机制整个删掉？** 第一版为了让每局都能收尾，加过月华加持与状元保底，两个都是**直接构造一副状元骰子**而不是掷出来的。结果是每局必定有状元、而且多半出现在保底那一刻——玩家博出来的不是自己的运气，是机制的排期。现在骰子在任何阶段都均匀随机，代价是约十分之一的牌局没有状元，换来的是「不论一秀还是状元，全看运气」这句话能站得住。
- **为什么是纯 CSS/SVG 美术？** 为了零外部依赖、零版权风险、任意分辨率不糊，以及最重要的一点——`npm install` 之后立刻就能跑，不需要下载任何素材。
- **为什么音效是合成的？** 同上。而且合成音效可以按奖项等级连续调参（`gong` 的音高、衰减时长），比找 13 个音效文件再对齐风格容易得多。
- **为什么份数是传统配比，而不是按概率算？** 因为传统会饼就长这样：1:2:4:8:16:32，一秀最多、状元只有一个。曾经有一版按「份数 ∝ 自然概率」配货，好处是五个池子的期望清空时间都落在 65~85 掷、谁都不是短板；代价是那组数字（31/17/4/3/1）跟中秋会饼没关系，玩家看不出所以然。现在换回传统份数，代价是**四进成了短板**——72% 的牌局最后都在等它那 8 份，一局因此长了一倍（中位从约 4.8 分钟涨到约 9 分钟）。

- **为什么份数与人数无关？** 因为一张会饼本来就是定量的，人多人少都是这一张。副作用是**局长度与人数无关**（2 人和 15 人都约 220 掷），听起来反直觉，但它让「一局多长」变成一个与房间规模无关的常数，好预测也好调。
- **为什么明知没有上限也不给牌局加个封顶？** 加封顶就得回答「封顶那一刻状元算谁的」，而任何答案都会把「博到饼尽」变成「博到时间到」。长尾是这套规则的固有性质（四进 4% × 要博满 8 份，对堂 1.5% × 2 份紧随其后），p99 约 19 分钟，实际发生的概率很低。真嫌长，把 `server/src/config/prizes.ts` 里四进的份数调下来（或者放宽它的判定条件）比加封顶干净得多。
- **为什么统计不做持久化？** 后台统计只供维护和联机验收使用，页面已经不展示这些数字；为此引入数据库没有必要。
- **为什么房主一走就散桌，还一点宽限都不给？** 见 [房主离席 = 整桌作废](#房主离席--整桌作废)。这是一条明确要求换来的取舍：散伙要够干脆，就得接受「刷新一次的房主会把全桌一起带走」。真觉得太狠，加宽限期是一个很小的改动（把 `closeIfHostLeft` 改成起一个定时器即可），但那就得同时回答「宽限期内牌局算谁的」这个问题。

## 本地管理员测试台

运行 `npm run dev`，点击页面右下角「管理员测试」，或打开
`http://localhost:5173/?admin=1`（端口以启动输出为准）。

- 一键测试全部 13 种奖项，预设包含打乱顺序的骰子，方便确认中奖组合置左。
- 六个下拉框可指定点数，点击「测试这组点数」查看结果。
- 可播放实际掷骰和开奖动画；取消动画勾选后立即展示结果。
- 测试台复用正式游戏的判奖函数、骰子组件和开奖动画，不需要开桌。
- 这是开发版的独立测试页面，不会写入正式牌局的积分或库存，也不提供线上管理员权限。生产构建不包含此入口。
